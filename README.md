# 学情闭环 Xueqing

> 面向教培机构的教学协作与学生成长闭环系统

## 项目状态

**Foundation v0.2｜架构打磨阶段，尚未进入真实机构生产使用。**

当前仓库已经明确产品边界、多人账号与权限原则、核心数据模型和开发路线；`lib/` 目前只是 Flutter 源码占位，并不是完整的 Flutter 工程脚手架。下一阶段应先完成正式 Flutter 初始化和 Supabase Development 环境，再进入业务开发。

> 在安全、权限、备份与合规检查完成前，禁止录入真实学生、家长或教师隐私数据。

## 为什么做这个产品

现有 Excel 原型已经形成一条有价值的教学链路：

**学生档案 → 发现问题 → 教学干预 → 再次检测 → 稳定解决 / 继续跟进 → 家校反馈 → 阶段复盘**

软件化的目标不是把 8 张 Sheet 搬到屏幕上，而是把这条链路变成多人协作、可追溯、低填写负担的日常工作流。

系统重点回答三个问题：

1. **学生现在最需要解决什么？**
2. **老师下一步应该做什么？**
3. **教学之后，问题是否有证据表明已经稳定解决？**

## 产品核心

### 1. 一份连续学生主档案
同一机构内，一个学生只存在一份主档案。升年级、换老师、换班、换校区都保留历史，不重新建档。

### 2. 多学科学情线
每个学生下面按学科形成连续学情。教师默认深度访问自己负责的学科，跨学科只共享必要摘要与综合观察。

### 3. 学情案例闭环
每个可独立跟进的问题形成一个 `learning_case`：

**发现 → 确认 → 干预 → 验证 → 稳定 → 关闭**

复发时重新打开原案例，而不是不断复制新问题。

### 4. 下一步行动驱动
任何未结束的学情案例都应能形成明确的下一步行动，直接进入教师“今日”工作台。

### 5. 事实只记录一次
周度跟进、顽固问题、阶段报告等尽量由课程、案例、证据、检测等原始事实自动推导，避免重复填写。

## 总体技术方向

```text
Windows / Android Flutter App
          │
          ├──── 普通业务读写 ────► Supabase Data API
          │                         └─ PostgreSQL + RLS
          │
          └──── 高权限操作 ──────► Supabase Edge Functions
                                    └─ 邀请成员 / 角色变更 / 学生合并等

Supabase Auth     → 登录与会话
Supabase Storage  → 私有附件
GitHub            → 源码、迁移、Issue、PR、CI
```

Flutter 客户端只能使用可公开的 Publishable Key；任何 Secret Key / service_role key 都不得进入客户端或 GitHub。

## V1 真正要做到的事情

V1 不追求功能数量，而追求一个小而完整的机构协作闭环：

- 管理员能建立机构成员与权限；
- 两个老师用不同账号登录并访问同一个学生的权限化数据；
- 学生只有一份机构主档案；
- 教师能建立学情案例、附证据、记录干预和验证；
- 未解决案例有下一步行动并进入“今日”；
- 常规课后记录目标控制在 30–60 秒；
- 教师交接后历史完整保留；
- 不同机构之间数据库层严格隔离；
- 所有关键状态变化可追溯。

## 明确不做

V1 暂不做：

- 排课收费 CRM
- 大型题库
- 成绩预测或虚构“学情总分”
- AI 自动诊断后直接修改正式学情
- 家长独立 App / 学生独立 App
- 复杂离线编辑与 Google Docs 式同字段实时协作
- 大量第三方登录

## 项目铁律

1. 一个学生只有一份机构主档案。
2. 原始事实只录一次，派生数据尽量自动计算。
3. 重要学情结论尽量有证据。
4. 未解决案例必须能明确下一步行动。
5. 数据归机构，人员变动不能破坏历史。
6. 权限必须在数据库/服务端执行，不能只靠隐藏按钮。
7. 老师少填一次，系统多自动一次。
8. AI 只做副驾驶，不静默替教师下正式结论。
