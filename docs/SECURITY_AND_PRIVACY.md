# 安全与隐私基线

> 本文是 V1 开发的最低安全要求。系统涉及未成年学生信息，任何功能实现不得以“先跑起来”为理由绕过这些要求。

## 1. 数据分类

### A. 身份与联系信息（高敏感）
- 学生姓名
- 家长姓名与联系方式
- 教师联系方式
- 学校、班级等可组合识别信息

### B. 教学与学情信息（敏感）
- 学情问题、作业、试卷、作文、测验
- 课堂观察
- 家校沟通
- 成长报告

### C. 系统元数据
- 用户 ID、机构 ID、角色、操作时间、对象 ID

开发与测试环境仅允许使用虚构数据。

## 2. 客户端密钥边界

Flutter 客户端只允许持有 Supabase Publishable Key（或旧项目中的 anon key）。客户端不得出现任何 Secret Key / service_role key / 数据库密码。

高权限动作必须在受信任的服务端环境执行，例如 Supabase Edge Functions：
- 邀请/停用机构成员
- 修改高权限角色
- 合并重复学生
- 跨组织管理操作
- 需要绕过普通 RLS 的维护任务

## 3. 数据库访问

所有对客户端开放的业务表必须：
1. 显式启用 RLS；
2. 按最小权限设置 GRANT；
3. 分别验证 SELECT / INSERT / UPDATE / DELETE；
4. 默认拒绝跨机构访问；
5. 对敏感跨学科数据默认拒绝，而不是默认开放。

前端隐藏按钮不构成安全控制。

## 4. 多租户隔离

- 机构级数据必须可明确归属到 organization_id。
- RLS 的首要条件是当前用户存在有效 organization_membership。
- 普通教师的业务访问还必须继续检查师生关系、学科关系或角色能力。
- 任何跨机构查询都必须被数据库策略拒绝，即使客户端手工构造请求。

## 5. 审计原则

必须记录关键动作，但审计日志不能无节制复制完整敏感文本。

建议记录：
- actor_user_id
- organization_id
- entity_type / entity_id
- action
- changed_fields
- request/operation id（如有）
- occurred_at

只有确有追溯需要的高风险变更才保存脱敏后的 before/after 摘要。避免把完整家长沟通、学生作文等再次复制进 audit_logs。

## 6. 删除与保留

- 教师离职：停用 membership，不删除其历史教学记录。
- 学生退班：默认归档，不直接硬删除。
- 普通教师不得执行核心业务硬删除。
- 合并学生必须保留 merge 记录和原始 ID 映射。
- 真正的数据删除/导出需求应作为管理员受控流程处理。

## 7. 附件

试卷、作文图片等附件默认使用私有 Storage Bucket：
- 不使用公开 bucket；
- 访问通过授权策略或短时签名 URL；
- 文件路径包含 organization_id 与不可猜测 ID；
- 不用真实姓名作为公开文件名。

## 8. 环境隔离

至少区分：
- development：虚构数据
- production：真实机构数据

正式上线前增加独立 staging 环境（条件允许时）。生产数据库迁移必须使用版本化 migration，不直接依赖人工 Dashboard 修改。

## 9. 上线前门槛

正式录入真实学生数据前至少完成：
- RLS 测试覆盖关键表与角色；
- 管理员高权限操作走服务端；
- 密钥扫描与 .gitignore 检查；
- 数据备份/恢复方案演练；
- 账号停用与教师交接演练；
- 学生合并/查重策略验证；
- 日志中无密码、token、密钥或完整敏感正文；
- 根据实际部署地区完成未成年人个人信息、机构授权与数据合规评估。
