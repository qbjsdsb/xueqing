# 开发路线

## 总原则

开发顺序遵循：**先底座，再垂直闭环，再扩展。**

每个阶段都必须有可验证的用户场景，不以“写了多少页面”衡量进度。

---

## Phase 0｜工程与安全底座

目标：得到一个可重复构建、可连接开发数据库、不会泄漏密钥的正式工程。

### Flutter
- [ ] 用官方工具正式初始化 Flutter 工程
- [ ] 启用 Windows + Android
- [ ] 建立 feature-first 目录
- [ ] 建立基础主题、路由、错误处理
- [ ] 建立静态分析与基础测试

### Supabase Development
- [ ] 建立 Development 项目
- [ ] 配置 Auth
- [ ] 建立 migration 目录
- [ ] 创建 profiles / organizations / memberships
- [ ] 配置 Publishable Key
- [ ] 验证客户端无 Secret Key/service_role

### GitHub
- [ ] CI：格式 / analyze / test
- [ ] Secret scanning 基础检查
- [ ] PR 模板
- [ ] 数据库 migration 检查规则

### Phase 0 验收
- [ ] 新环境可按文档从零启动项目
- [ ] App 能连接 Development Supabase
- [ ] 未登录用户不能读取业务表
- [ ] 仓库不含真实业务数据和私密密钥

## Milestone 1｜账号、机构与租户隔离

目标：两名老师真正拥有不同账号，但属于同一机构。

- [ ] 登录 / 退出 / Session 恢复
- [ ] profiles
- [ ] organization_memberships
- [ ] membership_roles
- [ ] 管理员邀请成员（服务端）
- [ ] 停用成员
- [ ] RLS：跨机构隔离
- [ ] 权限测试：A 机构用户绝对读不到 B 机构数据

### 验收场景
1. 管理员邀请教师甲、教师乙；
2. 两人用不同账号登录；
3. 两人都属于机构 A；
4. 机构 B 的测试数据对两人完全不可见。

## Milestone 3｜第一条完整学情闭环

目标：先把一个案例真正从发现跑到验证，而不是同时开发很多半成品页面。

- [ ] learning_cases
- [ ] case_events
- [ ] case_evidence
- [ ] interventions
- [ ] assessments
- [ ] case_actions
- [ ] 状态机
- [ ] 复发 / reopen
- [ ] 案例时间轴
- [ ] 乐观并发基础

### 端到端验收

```text
发现“阅读概括漏点”
  ↓
建立案例 + 证据
  ↓
创建“相似题训练”行动
  ↓
记录干预
  ↓
创建“次课验证”行动
  ↓
记录 assessment
  ↓
进入 stable
  ↓
后续若复发 → reopen，历史仍完整
```

## Milestone 4｜课程与“今日”工作流

目标：让老师每天愿意打开，而不是让老师专门“填系统”。

- [ ] lessons / lesson_students
- [ ] lesson_case_actions
- [ ] 今日工作台
- [ ] 课前遗留与待验证
- [ ] 快速课中记录
- [ ] 30–60 秒课后完成流程

# V1｜机构内部试运行

当 Milestone 0–5 达成，才算 V1。

建议先选择少量真实教师、使用虚构或脱敏数据完成试运行；通过安全与合规门槛后，再录入真实学生数据。

## V1 核心验收标准

1. 两名教师能使用独立账号共同管理同一学生；
2. 学生主档案不因学科、老师、年级重复创建；
3. 学情案例从证据到验证全程可追溯；
4. 未结束案例具有下一步行动；
5. 教师日常记录足够快；
6. 教师离职/交接后历史完整；
7. 跨机构访问数据库层拒绝；
8. 普通教师无法越权修改其他学科核心结论；
9. 关键高权限动作不在 Flutter 客户端直接执行；
10. 无任何真实学生信息进入 GitHub。

## 每个 Milestone 的完成定义

功能只有同时满足以下条件才算完成：

- 正常流程可用；
- 权限路径验证；
- 错误/空状态可理解；
- 核心逻辑有测试；
- schema 变化有 migration；
- 不引入真实隐私数据；
- 文档同步更新；
- 不破坏已有端到端验收场景。
