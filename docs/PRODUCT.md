# 产品蓝图

## 1. 产品名称与定位

**学情闭环（Xueqing）**

副标题：**机构教学协作与学生成长闭环系统**

它不是传统教务 CRM，也不是 Excel 网页化。核心价值是把真实教学过程沉淀为连续、可协作、可验证的学生成长记录，并让这些记录反过来指导下一次教学。

## 2. 产品北极星

系统始终围绕一个判断：

> **老师打开软件后，能否更快知道这个学生下一步应该做什么，并且能用证据判断前一次教学是否真正有效？**

任何不能改善这个闭环、只增加填写负担的功能，都应推迟、自动化或删除。

## 3. 主要用户

### 任课教师
关心：今天需要处理什么、学生上次遗留什么、这次做什么、课后如何快速留下一条可靠记录。

### 学生负责人 / 学管 / 班主任
关心：学生跨学科整体状态、多个老师的共同观察、需要协调的风险和家校沟通。

### 学科负责人
关心：本科组长期未解决问题、高频共性问题、可沉淀的有效教研方案。

### 教务 / 机构管理员
关心：机构数据完整性、成员权限、学生归属、教师交接、异常与整体教学质量。

> 管理端不应把“老师填了多少条记录”作为核心 KPI，否则系统会迅速退化为应付式填表工具。

## 4. 核心领域对象

### 4.1 学生主档案 Student
同一机构内一个真实学生只保留一份主档案。姓名相同不代表同一人，查重与合并必须是受控流程。

### 4.2 学生学科档案 Student Subject Profile
学生在某一学科上的连续档案。换老师不新建，教师只是阶段性负责人。

### 4.3 学情案例 Learning Case
可独立跟进的学习问题，是教学闭环最小业务单元。

一个案例至少回答：
- 问题是什么；
- 在什么证据中发现；
- 当前原因判断是什么；
- 做过哪些干预；
- 如何验证；
- 验证结果如何；
- 是否复发；
- 下一步做什么。

### 4.4 证据 Evidence
试卷、作文、课堂练习、小测、作业、客观观察等，用来支撑判断，而不是为了“上传更多材料”。

### 4.5 教学干预 Intervention
老师针对某个案例真正做过的处理方法。

### 4.6 验证 Assessment
用于判断干预是否有效的后续检测。验证结果必须和“老师感觉有进步”区分开。

### 4.7 下一步行动 Case Action
未结束案例的明确待办，例如：次课小测、相似题迁移、重新讲解、原因复盘、与家长沟通。它是“今日工作台”的主要事实来源。

### 4.8 综合观察 Observation
跨学科必要共享的客观观察，例如连续未交作业、课堂后半段注意力下降。避免人格化标签和未经授权的敏感推断。

## 5. 学情案例生命周期

建议状态：

`new → confirmed → intervening → pending_verification → stable → closed`

状态语义必须明确：
- **new**：刚发现，尚未完成教师确认；
- **confirmed**：确认值得独立跟进，并已有初步判断；
- **intervening**：正在实施教学干预；
- **pending_verification**：当前干预已完成，等待迁移/后续验证；
- **stable**：已有证据支持明显改善，但仍处于观察期；
- **closed**：当前不再作为主动跟进事项，没有未完成主行动；并不意味着“永远不会复发”。

允许：
- `stable / closed → reopened`（复发后重新打开原案例）；
- 验证失败后重新进入 `intervening`；
- 教师在说明原因后撤销误建案例。

不允许用一次 `passed` 自动等同于 `stable/closed`。状态变化必须写入案例事件时间轴。

## 6. 分类体系：既要结构化，也不能把老师困死

为了以后能做“机构高频问题”和教研分析，不能只依赖自由文本，否则会出现“现代文阅读 / 阅读理解 / 阅读”三套口径。

V1 采用两层表达：
- **受控分类**：学科 → 模块/能力节点，用于统计和检索；
- **自由标题/描述**：保留老师对真实问题的自然表达。

分类体系允许机构配置和逐步扩展，但不在 V1 先建设庞大的知识图谱。

## 7. Excel 原型软件化原则

原 Excel 里的 8 张工作表不是 8 个软件模块。

- 学生档案 → Student / Enrollment / Assignment
- 初诊问题 → Learning Case
- 知识闭环 → Evidence + Intervention + Assessment + Case Event
- 周度跟进 → 从课程和案例事件自动汇总
- 顽固问题 → 根据重复失败/复发规则生成重点提示，不维护第二份台账
- 家校沟通 → Parent Communication
- 阶段复盘 → 从事实数据生成报告草稿/快照

详见 `EXCEL_TO_PRODUCT.md`。

## 8. 产品目标导航与 V1 导航必须分开

### 完整产品目标导航
成熟后教师端可以形成 6 个一级入口：
1. **今日**
2. **学生**
3. **课程**
4. **学情**
5. **家校**
6. **报告**

### V1 首发导航
V1 只保证 4 个核心入口可用：
1. **今日**：到期行动、重点待办、快速进入学生/课程；
2. **学生**：连续档案与当前重点；
3. **课程**：快速开始/完成一次真实教学记录；
4. **学情**：案例、证据、干预、验证与下一步行动。

“家校”和“报告”在 V1.1 再成为正式一级入口，避免第一版同时铺太多半成品。

## 9. “今日”不等于排课系统

V1 明确不做完整排课 CRM，因此“今日”不能假设系统天然知道老师今天的全部课表。

V1 的“今日”主要来自：
- 今日/逾期的 `case_actions`；
- 教师自己最近负责的学生；
- 待验证案例；
- 高优先级未解决案例；
- 可选的轻量课程计划（若后续确有需要）。

教师应能从“今日”或“学生”直接 **快速开始一次课程**，而不是先维护一套复杂课表。

未来若机构已有第三方排课系统，优先考虑导入/集成，而不是把本项目扩张成收费排课 CRM。

## 10. 核心教师流程

### 10.1 课前：30 秒理解上下文
系统展示：
- 上次遗留；
- 本次到期验证；
- 高优先级未解决案例；
- 最近关键观察；
- 本次建议行动。

### 10.2 课中：只记录新事实
教师可以：
- 完成/调整已有行动；
- 添加证据；
- 新增学情案例；
- 记录实际干预；
- 记录验证结果。

不要求老师重写“本周总结”。

### 10.3 课后：30–60 秒完成常规记录
完成课程时，系统根据本次事实：
- 确认本次处理了哪些案例；
- 完成/取消旧行动；
- 必要时生成下一步行动草稿；
- 写入案例时间轴；
- 刷新“今日”；
- 为未来家校反馈和阶段报告提供事实源。

系统可以给建议，但正式状态变化仍应清楚展示给教师确认，避免“点完成课程后后台偷偷改一堆事实”。

## 11. 网络失败时不能让老师白填

V1 仍是 **online-first**，云数据库是唯一正式事实源，但高频输入必须具备最小抗失败能力：
- 编辑中的表单保留本地临时草稿；
- 提交中显示明确保存状态；
- 短暂网络失败允许重试，不清空输入；
- 服务端未确认成功前，不在 UI 中伪装成“已保存”；
- 不做复杂离线多主同步。

这不是“离线系统”，而是避免老师下课记录因一次网络抖动全部丢失。

## 12. 跨学科协作

采用 **默认隔离、必要互通**：
- 本科教师：本科详细数据可见，并按责任范围编辑；
- 其他任课教师：默认只看综合摘要、必要风险和获准共享的观察；
- 学生负责人/学管：拥有综合视角，但不随意改写各学科专业结论；
- 学科负责人：本科组范围；
- 管理员：机构治理视角。

“能看到”与“能修改”必须分开设计。

## 13. V1 产品边界

### V1 必须有
- 登录、机构成员关系与首位管理员初始化；
- 学生主档案与重复提示；
- 教师—学生—学科关系及交接；
- 学情案例、受控分类、证据、干预、验证；
- 下一步行动；
- 快速课程记录；
- 今日工作台；
- 权限、审计与基本并发保护；
- 网络失败时不丢当前输入。

### V1 可以很简单
- 附件只支持少量私有上传；
- 管理端只做成员/学生治理和必要异常；
- 学生合并先做受控管理员流程；
- 搜索只覆盖高频字段，不追求全文检索平台。

### V1 明确不做
- 收费排课 CRM；
- 大型题库；
- 学情综合分/健康分；
- 成绩预测；
- 家长端、学生端；
- AI 自动下正式诊断；
- 复杂离线双向同步；
- Google Docs 式多人同时编辑同一字段；
- 大量第三方登录。

## 14. V1 成功指标

产品是否成功，不看页面数量，先看：
1. **记录负担**：常规课后记录中位时间 ≤ 60 秒；
2. **连续性**：教师交接后，新教师能快速看懂历史重点与下一步；
3. **闭环完整性**：未结束案例中绝大多数存在明确主行动或明确“暂不安排”的理由；
4. **可追溯**：关键状态变化能追到谁、何时、依据什么；
5. **协作正确性**：两位老师看到的是同一个学生，但编辑范围符合权限；
6. **数据一致性**：周度/阶段汇总不需要教师重复录入即可生成；
7. **保存可靠性**：网络短暂失败不会让教师丢失正在编辑的高频记录；
8. **安全性**：跨机构数据访问在数据库层被拒绝。

## 15. UX 铁律

- 默认展示“下一步”，而不是展示数据库结构；
- 高频操作尽量一屏完成；
- 能点选就不强迫长文本；
- 自动生成内容必须能看见依据与确认结果；
- 重要状态不只依赖颜色表达；
- 表单保存状态必须明确：未保存 / 保存中 / 已保存 / 失败；
- 手机负责快速记录，Windows 负责深度查看和管理，但两端共享同一业务模型；
- 不为了“功能完整”把低频管理员操作塞进教师主界面。

## 16. AI 边界

AI 适合：
- 自然语言转结构化草稿；
- 相似/重复案例提示；
- 课程和阶段摘要；
- 家长反馈草拟；
- 教研案例检索。

AI 不得：
- 静默新建、关闭或改写正式学情案例；
- 在没有教师确认时给学生贴长期能力/人格标签；
- 绕过权限访问不应看到的数据；
- 把生成文本当成证据本身。

## 17. 产品铁律

1. 一个学生只有一份机构主档案。
2. 事实只记录一次，派生信息自动计算。
3. 重要结论尽量有证据。
4. 未结束案例必须能明确下一步行动或明确暂停原因。
5. 学生历史不能因换老师、升年级而断裂。
6. 数据共享必须与编辑权限分离。
7. 老师少填一次，系统多自动一次。
8. 网络失败不能让高频记录凭空消失。
9. 不把“今日”偷偷做成排课 CRM。
10. AI 只做副驾驶。
