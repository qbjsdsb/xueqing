# 产品蓝图

## 1. 产品名称与定位

**学情闭环（Xueqing）**

副标题：**机构教学协作与学生成长闭环系统**

它不是传统教务 CRM，也不是 Excel 网页化。核心价值是把真实教学过程沉淀为连续、可协作、可验证的学生成长记录，并让这些记录反过来指导下一次教学。

## 2. 产品北极星

系统始终围绕一个判断：

> **老师打开软件后，能否更快知道这个学生下一步应该做什么，并且能用证据判断前一次教学是否真正有效？**

任何不能改善这个闭环、只增加填写负担的功能，都应推迟或删除。

## 3. 主要用户

### 任课教师
关心：今天教谁、上次遗留什么、这次处理什么、课后怎么快速记录。

### 班主任 / 学管
关心：学生跨学科整体状态、多个老师的共同观察、需要协调的风险和家校沟通。

### 学科负责人
关心：本科组长期未解决问题、高频共性问题、可沉淀的有效教研方案。

### 教务 / 机构管理员
关心：机构数据完整性、成员权限、学生归属、教师交接、异常与整体教学质量。

> 管理端不应把“老师填了多少条记录”当成主要 KPI，否则系统会迅速退化为应付式填表工具。

## 4. 核心领域对象

### 4.1 学生主档案 Student
同一机构内一个真实学生只保留一份主档案。姓名相同不代表同一人，查重与合并必须是受控流程。

### 4.2 学生学科档案 Student Subject Profile
学生在某一学科上的连续档案。换老师不新建，教师只是阶段性负责人。

### 4.3 学情案例 Learning Case
可独立跟进的学习问题，是教学闭环最小业务单元。

一个案例至少回答：
- 问题是什么；
- 在什么证据中发现；
- 当前原因判断是什么；
- 做过哪些干预；
- 何时验证；
- 验证结果如何；
- 是否复发；
- 下一步做什么。

### 4.4 证据 Evidence
试卷、作文、课堂练习、小测、作业、观察等，用来支撑判断，而不是为了“上传更多材料”。

### 4.5 教学干预 Intervention
老师针对某个案例真正做过的处理方法。

### 4.6 验证 Assessment
判断干预是否有效的后续检测。验证结果必须和“老师感觉有进步”区分开。

### 4.7 下一步行动 Case Action
未结束案例的明确待办，例如：次课小测、相似题迁移、重新讲解、与家长沟通。它是“今日工作台”的事实来源。

### 4.8 综合观察 Observation
跨学科必要共享的客观观察，例如连续未交作业、课堂后半段注意力明显下降。避免人格化标签。

## 5. 学情案例生命周期

建议状态：

`new → confirmed → intervening → pending_verification → stable → closed`

允许：
- `stable / closed → reopened`（复发后重新打开）；
- 从 `intervening` 回到继续干预；
- 教师在说明原因后撤销误建案例。

不建议：
- 直接从 `new` 一键跳成 `closed`；
- 通过编辑历史文本“假装”状态从未发生过。

状态变化写入案例事件时间轴。

## 6. Excel 原型软件化原则

原 Excel 里的 8 张工作表不是 8 个软件模块。

- 学生档案 → Student / Enrollment / Assignment
- 初诊问题 → Learning Case
- 知识闭环 → Evidence + Intervention + Assessment + Case Event
- 周度跟进 → 从课程和案例事件自动汇总
- 顽固问题 → 根据重复失败/复发规则生成重点标签，不维护第二份台账
- 家校沟通 → Parent Communication
- 阶段复盘 → 从事实数据生成报告草稿

详见 `EXCEL_TO_PRODUCT.md`。

## 7. 教师端信息架构

V1 一级入口保持 6 个：

1. **今日**：今天需要处理的人和事
2. **学生**：连续学生档案与学科学情
3. **课程**：课程记录与快速课后记录
4. **学情**：未结束案例、待验证、长期问题
5. **家校**：沟通记录与反馈草稿
6. **报告**：阶段变化与可分享总结

管理功能根据角色进入二级入口，不挤占普通教师主导航。

## 8. 核心教师流程

### 8.1 课前：30 秒理解上下文
系统展示：
- 上次遗留；
- 本次到期验证；
- 高优先级未解决案例；
- 最近关键观察；
- 本次建议行动。

### 8.2 课中：只记录新事实
教师可以：
- 标记已有行动结果；
- 添加证据；
- 新增学情案例；
- 记录必要干预。

不要求老师重写“本周总结”。

### 8.3 课后：30–60 秒完成常规记录
点击完成课程后，系统根据本次事实：
- 更新案例状态；
- 完成/生成下一步行动；
- 写入教学时间轴；
- 更新今日待办；
- 为家长反馈和阶段报告提供数据源。

## 9. 跨学科协作

采用 **默认隔离、必要互通**：

- 本科教师：本科详细数据可见，并按责任范围编辑；
- 其他任课教师：默认只看综合摘要、必要风险和获准共享的观察；
- 班主任/学管：拥有学生综合视角，但不随意改写各学科专业结论；
- 学科负责人：本科组范围；
- 管理员：机构治理视角。

“能看到”与“能修改”必须分开设计。

## 10. V1 产品边界

### V1 必须有
- 账号登录与机构成员关系；
- 学生主档案与查重/合并基础流程；
- 教师—学生—学科分配；
- 学情案例、证据、干预、验证；
- 下一步行动；
- 课程与快速记录；
- 今日工作台；
- 权限与审计；
- 教师交接。

### V1 可以很简单
- 家校反馈先做结构化记录，不追求复杂 AI；
- 报告先做基础汇总；
- 管理驾驶舱只做异常和事实指标；
- 附件先支持少量私有上传。

### V1 明确不做
- 收费排课 CRM；
- 大型题库；
- 学情综合分/健康分；
- 成绩预测；
- 家长端、学生端；
- AI 自动下正式诊断；
- 复杂离线双向同步；
- Google Docs 式多人同时编辑同一字段。

## 11. V1 成功指标

产品是否成功，不看页面数量，先看：

1. **记录负担**：常规课后记录中位时间 ≤ 60 秒；
2. **连续性**：教师交接后，新教师能快速看懂历史重点与下一步；
3. **闭环完整性**：未结束案例中绝大多数存在明确下一步行动；
4. **可追溯**：任何关键状态变化能追到谁、何时、依据什么；
5. **协作正确性**：两位老师看到的是同一个学生，但编辑范围符合权限；
6. **数据一致性**：周度/阶段汇总不需要教师重复录入即可生成；
7. **安全性**：跨机构数据访问在数据库层被拒绝。

## 12. UX 铁律

- 默认展示“下一步”，而不是展示数据库结构；
- 高频操作尽量一屏完成；
- 能点选就不强迫长文本；
- 系统自动生成的内容必须允许老师查看依据；
- 不用虚构分数制造“科学感”；
- 重要状态有明确语言，不依赖颜色才能理解；
- 手机负责快速记录，Windows 负责深度管理，但两端共享同一业务模型。

## 13. AI 边界

AI 适合：
- 自然语言转结构化草稿；
- 相似/重复案例提示；
- 课程和阶段摘要；
- 家长反馈草拟；
- 教研案例检索。

AI 不得：
- 静默新建或关闭正式学情案例；
- 在没有教师确认时给学生贴长期能力/人格标签；
- 绕过权限访问不应看到的数据；
- 把生成文本当成证据本身。

## 14. 产品铁律

1. 一个学生只有一份机构主档案。
2. 事实只记录一次，派生信息自动计算。
3. 重要结论尽量有证据。
4. 未结束案例必须能明确下一步行动。
5. 学生历史不能因换老师、升年级而断裂。
6. 数据共享必须与编辑权限分离。
7. 老师少填一次，系统多自动一次。
8. AI 只做副驾驶。
