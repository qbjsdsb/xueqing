# Leadership Teaching Model｜领导教学方法论事实源

状态：Phase 0A.6 product foundation draft  
来源：用户提供的《学情档案 Excel 化原型 v0.1（审校版）》及现有 Xueqing Foundation。  
用途：保存领导真正希望机构执行的教学管理方法；**不是页面清单，也不是数据库 schema。**

---

## 1. 核心结论

领导 Excel 的核心不是“建立一套学情档案”，而是一套**责任制教学闭环**：

```text
理解学生
→ 初诊发现问题
→ 判断原因与优先级
→ 明确责任人和整改方案
→ 实施干预
→ 多次验证
→ 未解决则跨周继续 / 重新分析
→ 必要时家校协同
→ 阶段复盘
→ 下一阶段继续
```

一句话定义：

> **发现—整改—验证—再整改—协同—复盘，直到问题有足够证据支持稳定解决。**

软件化的目标不是削弱这套管理要求，而是：

> **保留领导的责任闭环，把 Excel 才需要的重复录入、跨表关联、人工统计、人工追踪交给系统。**

---

## 2. Excel 是理念载体，不是产品结构

Excel 当前采用 8 张 Sheet：

1. `00_说明与规则`
2. `01_学生档案`
3. `02_初诊问题`
4. `03_知识闭环`
5. `04_周度跟进`
6. `05_顽固问题`
7. `06_家校沟通`
8. `07_阶段复盘`

这些 Sheet **不得一一映射为软件一级页面或数据库表**。

Excel 自身也明确说明：
- 当前“一个工作簿对应一个学生的一门学科”只是原型假设；若做全机构集中管理，需要升级为多学生模型；
- 问题编号、优先级、状态、责任人、下次跟进等部分字段属于 Excel 化时的管理建议，不全部等于原 Word 原始事实；
- 原型不擅自增加复杂评分、仪表盘或自动提醒；
- 家长联系方式应在学生档案维护，沟通页只记录沟通事件，避免重复敏感信息。

因此 Xueqing 应继承**方法和责任语义**，而不是继承 Excel 的物理布局。

# 3. 第一层：先理解学生，再管理问题

`01_学生档案` 同时要求：
- 学员姓名；
- 授课学科；
- 年级；
- 授课老师；
- 试听/建档日期；
- 上课频次；
- 家长联系方式；
- **学员学情定位**；
- **学员学科优势 / 课堂优势**；
- 档案状态；
- 最近更新日期。

其中“学情定位”和“优势”说明：

> 领导并不希望系统只记录学生的缺点。

### 产品原则

Student / Student Subject Profile 必须能够表达：
- 当前学习背景；
- 当前学情定位；
- 已观察到的优势；
- 当前最重要的问题/下一步。

但不得把学生简化为一个固定“能力分”或永久标签。

### Excel 当前定位下拉

原型中存在：
- 基础薄弱
- 中等待提升
- 中等稳定
- 培优拔高

这些选项反映领导需要**快速形成当前教学定位**，但 Phase 0A.6 不直接把四档标签冻结成永久数据库枚举。

原因：
1. 定位会随时间变化；
2. 不同学科可不同；
3. 需要避免标签覆盖具体 Evidence/Case；
4. 未来最好表达“当前教学定位 + 更新时间/来源”，而不是学生人格标签。

### 优势原则

优势必须：
- 与学习/课堂相关；
- 尽量基于可观察事实；
- 可随学科不同；
- 不要求量化评分；
- 不因存在问题而被隐藏。

# 4. 第二层：Initial Diagnosis 是正式入口

`02_初诊问题` 的工作语言是：

> **试听初诊 · 三类问题总台账**

一条问题要求表达：
- 问题编号；
- 问题分类；
- 具体问题表现；
- 问题根本原因；
- 初步整改方案；
- 优先级；
- 当前状态；
- 首次发现日期或周次；
- 责任人；
- 备注。

### 三类问题

领导明确把问题分为：

1. **知识漏洞**
2. **学习习惯**
3. **考试技巧**

这不是三个标签颜色，而是三个不同教学问题类型。

### 初诊的真实业务目的

初诊要回答：

```text
这个学生当前在哪里？
擅长什么？
主要问题是什么？
问题属于什么类型？
为什么会出现？
先处理哪个？
谁负责？
下一步是什么？
```

### 软件化原则

Initial Diagnosis 应成为一个正式 workflow：

```text
Student
→ Subject Profile
→ 当前定位 / 优势
→ 发现候选问题
→ 三类问题分类
→ 优先级
→ 教师确认哪些值得正式跟进
→ Learning Case
→ first primary Action
```

不建立一套永久与 Learning Case 平行的“初诊问题台账”。

初诊是 **Case 的来源场景**，不是第二套 Case 数据库。

---

# 5. 第三层：知识问题实行“三阶订正”

`03_知识闭环` 是领导方法论中最鲜明的部分：

```text
当堂订正
→ 课后相似题巩固
→ 次课小测 / 延迟独立验证
→ 清零 / 跨周跟进
```

Excel 当前下拉口径：

### 一阶订正状态
- 完成订正
- 未完全理解

### 二阶巩固状态
- 全部完成
- 部分出错
- 未完成

### 三阶小测结果
- 满分通关
- 仍有漏洞
- 需要再次跟进

### 最终闭环状态
- 已清零
- 跨周跟进

这些选项揭示一个关键业务事实：

> **第三阶结果和“最终清零”是两个概念。**

即使某次小测表现很好，仍然需要教师根据整体证据决定是否可以认为问题真正解决。

### Xueqing 的继承方式

三阶订正应被保留为**知识类 Case 的默认教学 Workflow Template**，但不能做成数据库固定三列。

底层仍使用：
- Evidence；
- Intervention；
- Assessment；
- Case Action；
- Case Event。

这样才能支持：
- 某问题需要两次二阶练习；
- 三阶失败后重新干预；
- 某些知识问题不需要完全相同的题量；
- 历史完整留痕；
- reopen 后继续使用同一 Case。

### 禁止

不得因为底层已经泛化为 Assessment/Action，就把教师界面中的“三阶订正”语言完全删除。

> 数据模型可以通用，教学语言必须让机构老师仍然认得领导的方法。

---

# 6. 第四层：“清零”是强结果词

Excel 多处使用：
- 已清零；
- 跨周跟进；
- 已彻底清零。

初诊状态下拉甚至区分：
- 未开始
- 整改中
- 已改善
- 已清零
- 持续跟进

顽固问题状态则只有：
- 持续跟进
- 已彻底清零

说明“清零”不是“这一次做对了”，而是领导体系里的**退出主动问题管理的强判断**。

### Foundation 对齐

Xueqing 继续保持：

```text
Assessment passed
≠ stable
≠ closed
```

推荐教学语言映射：

```text
Assessment passed
= 本次验证通过

pending_verification
= 等待教师判断

stable
= 已改善 / 稳定观察

closed
= 已清零（退出主动跟进）
```

但 `closed` 只有在教师确认问题不再需要 active tracking 时才能发生。

### “彻底清零”

Excel 对顽固问题使用“已彻底清零”。产品层可以作为强调性结果文案，但**不新增第二个 closed 状态**。

---

# 7. 第五层：周度跟进是节奏，不是第二份周报

`04_周度跟进` 每周记录：
- 本节课授课内容；
- 旧问题整改进度；
- 当周新增问题；
- 本周针对性整改动作；
- 周度复盘结论；
- 下周重点；
- 记录人。

周度复盘下拉包括：
- 初见改善
- 无变化
- 需调整方案
- 持续改善
- 卡点未突破
- 需强化训练

真正方法论是：

```text
回看旧问题
+ 发现新问题
+ 记录本周实际动作
+ 判断有没有效果
+ 确定下周重点
```

### 软件化原则

不得要求老师课后已经记录完 Lesson / Case / Evidence / Intervention / Assessment / Action 后，再手工抄一遍“周度跟进”。

系统应从真实事实自动派生：
- 本周处理过哪些 Case；
- 新增哪些 Case；
- 做过哪些 Intervention；
- 哪些 Assessment passed/partial/failed；
- 哪些 Case 进入 stable/closed/reopen；
- 哪些 primary Action 进入下周。

老师只在确有专业价值时补充一个**周度综合判断**，而不是重新填流水账。

---

# 8. 第六层：顽固问题是升级后的同一 Case

`05_顽固问题` 明确：

> **只放多次整改仍未通关的问题。**

字段包含：
- 顽固问题编号；
- 问题分类；
- 具体顽固问题；
- 首次发现周次；
- 关联初诊问题编号；
- 逐周整改迭代过程；
- 最终整改结果；
- 当前状态；
- 最近跟进日期。

### 领域解释

“顽固”不是教师随手勾选的静态属性，而是由历史事实逐渐形成：
- 持续时间；
- 多次 Assessment partial/failed；
- 多轮 Intervention 后仍未稳定；
- stable 后复发；
- closed 后 reopen；
- 周期内长期没有有效进展。

因此 Foundation 当前规则保持：

> **顽固问题由同一 Learning Case 的历史派生，不维护第二套顽固问题表。**

### 产品表现

系统可以显示：

```text
长期重点
持续 6 周 · 3 次验证未通过 · reopen 1 次
```

并触发：

> **重新分析原因 / 调整方案**

而不是只让老师继续机械刷题。

---

# 9. 第七层：家校是整改协同，不是“报喜报忧”

`06_家校沟通` 的说明直接定义目的：

> 同步学生整改进度，反馈三阶订正结果，布置家校配合任务。

字段包括：
- 沟通日期或周次；
- 沟通对象；
- 沟通核心（三类问题 + 整改进度）；
- **家校配合整改要求**；
- 沟通结果；
- 下次沟通日期；
- 记录人。

当前沟通结果下拉：
- 已达成共识
- 待家长反馈
- 需继续跟进
- 已完成

### 产品含义

家校闭环应该是：

```text
真实教学事实
→ 整理成家长可理解的反馈
→ 教师/Advisor 确认
→ 实际沟通
→ 家庭配合要求
→ 家长回应
→ follow-up
→ 必要时重新进入教学 Case/Action
```

### 数据原则

- 联系方式只保存一次，不在每次沟通重复；
- “系统生成的反馈草稿”不能冒充“已经发给家长”；
- 实际沟通内容需要形成当时的冻结快照；
- 家长的回应是新的沟通事实，不应覆盖教师原有专业判断；
- 家庭配合任务不是 `assigned_membership_id` 的教师 Case Action，因为 guardian 不是机构 membership；
- 教师自己的 follow-up 可以形成 `communicate` Case Action。

---

# 10. 第八层：阶段复盘必须有人承担判断责任

`07_阶段复盘` 包含：
- 复盘阶段；
- 复盘日期；
- 复盘人；
- 本阶段整体进步；
- 现存遗留问题；
- 下一阶段整改计划；
- 授课老师签字；
- 总结日期。

Excel 还设计了初诊问题数、已清零数、跨周记录数、家校沟通次数等摘要。

### 领导真正需要的不是 Dashboard

摘要数字可以帮助整理，但不能替代复盘。

真正重要的是：

```text
系统整理事实
→ 老师看证据
→ 老师确认整体进步
→ 老师确认遗留问题
→ 老师制定下一阶段计划
→ 冻结确认记录
```

### 软件化“签字”

不要求手写签名图片。

可转换为审计事实：

```text
finalized_by = 某 membership
finalized_at = 时间
source_cutoff_at = 报告引用事实截止时间
```

这样比图片签名更可查询、更可审计。

---

# 11. 责任人 / 记录人 / 复盘人 / 签字的统一解释

Excel 多处要求：
- 责任人；
- 记录人；
- 复盘人；
- 授课老师签字。

这些并不是要求老师重复输入姓名，而是在表达：

> **重要事实和决定必须知道是谁产生、谁负责、谁确认。**

软件应尽量从登录 membership 自动记录：
- created_by；
- recorded_by；
- owner；
- assigned_to；
- assessed_by；
- finalized_by。

只有真正需要改变责任主体时才让用户主动选择人。

---

# 12. 问题编号的真正价值：可引用和可追踪

Excel 要求问题编号唯一，并由知识闭环/顽固问题关联。

软件不要求教师手工维护 `W-001`。

数据库内部使用稳定 ID；产品如果需要开会、沟通、交接时可读，可自动派生/生成一个机构内可读 Case code，例如：

```text
语文 · C-012
```

是否正式增加 human-readable Case code 留待 Data Model audit 决定。

关键是不允许因为 UI 不显示编号就失去跨时间追踪能力。

---

# 13. 上课频次的边界

Excel 学生档案包含：
- 每周 1 次；
- 每周 2 次；
- 其他。

这反映一个有用背景：同样“7 天未验证”，对于不同上课频次的学生意义可能不同。

但 Xueqing 不因此进入排课/课消系统。

Phase 0A.6 可评估将“常规教学频次/节奏”作为 Student Subject Profile 的轻量背景事实；真正的到期语义仍以 Case Action `due_at` 为事实源。

# 14. 从 Excel 到 Xueqing 的最终映射

| Excel 理念 | Xueqing 领域表达 | 是否独立台账 |
|---|---|---|
| 学生基础档案 | Student + Enrollment + Subject Profile + Assignments | 否 |
| 学情定位/优势 | Subject Profile 当前教学上下文/可观察优势 | 待模型审查 |
| 初诊三类问题 | Initial Diagnosis → Learning Case | 否 |
| 三阶订正 | Knowledge Case workflow template + Intervention/Assessment/Action | 否 |
| 周度跟进 | Lesson/Case/Action 事实的派生摘要 + 少量人工判断 | 否 |
| 顽固问题 | Case 历史派生长期重点 | 否 |
| 家校沟通 | Communication snapshot + home support + response + follow-up | 是，沟通事件本身是新事实 |
| 阶段复盘 | Period snapshot + teacher judgment + finalized confirmation | 是，冻结快照是新事实 |
| 老师签字 | membership + finalized_at/audit | 否图片签名 |

# 15. 必须守住的产品铁律

1. 一个学生在机构内只有一份稳定主身份。
2. 同一真实教学事实只记录一次。
3. 学生优势与问题同时存在，不能把系统变成缺陷清单。
4. 三类问题是不同教学问题，不只是三种颜色标签。
5. 三阶订正保留为知识类的机构教学语言和默认 workflow。
6. 一次验证通过绝不自动等于“清零”。
7. 顽固问题从历史事实派生，不维护第二套真假不一的台账。
8. 周度/阶段汇总尽可能从日常教学事实自动组织。
9. 家校沟通服务整改协同，而不是打卡式报喜报忧。
10. 重要结论由授权教师确认，AI/统计不能自动代替专业判断。
11. 老师少填一次，系统多自动一次。
12. 管理力度来自“事实连续、责任明确、异常可处理”，不是来自多填表。

---

# 16. Phase 0A.6 后续必须进一步冻结的决策

本文件冻结“领导理念”，但以下实现选择仍需其他事实源决定：

- 学情定位采用结构化档位、自由摘要，还是两者结合；
- 优势是否需要独立历史/观察对象，或先作为 Subject Profile summary；
- human-readable Case code 是否有真实使用价值；
- 常规上课频次是否进入 Subject Profile；
- 清零/closed 的具体 command preconditions；
- 三类 workflow template 是否需要显式模板版本；
- 家校沟通 snapshot 的字段边界；
- 阶段复盘 snapshot 的字段边界。

这些问题必须在 P0 Gate A/B 通过、provider/region/identity/session strategy 冻结并获 Go/No-Go 后进入 formal production migrations 前解决，但不得反过来改写本文件已经冻结的教学原则。

# 17. Fidelity acceptance test

任何未来实现都必须能够通过下面的问题：

> 如果领导拿着原 Excel 来问“我的初诊、三类问题、三阶订正、跨周、顽固问题、家校配合和阶段复盘在哪里”，产品是否能一一指出它们在新系统中的工作流，并证明没有因为技术抽象而丢失？

如果答案是否定的，即使数据库设计很漂亮，也视为**教学方法论迁移失败**。
