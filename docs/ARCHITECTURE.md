# 系统架构

## 1. 总体架构

客户端采用 Flutter，优先支持 Windows 与 Android；云端采用 Supabase；GitHub 负责源码与版本管理。

```text
Windows / Android
       │
       ▼
 Flutter Client
       │
       ▼
 Supabase
 ├─ Auth
 ├─ PostgreSQL
 ├─ Storage
 └─ Row Level Security
```

## 2. 多租户模型

系统从第一天支持多机构：

- organization：机构
- campus：校区
- user：账号
- staff_profile：员工资料
- role：角色
- membership：账号与机构关系

所有关键业务数据必须带 organization_id，禁止通过前端隐藏来代替真实权限控制。

## 3. 账号原则

账号代表“人是谁”，角色代表“能做什么”。

教师换岗、升任学科负责人、兼任班主任都不重新注册账号，只调整角色与业务关系。

教师离职时停用账号，不删除历史数据。

## 4. 权限模型

权限由以下因素共同决定：

- 所属机构
- 所属校区
- 系统角色
- 与学生的关系
- 所负责学科

建议组合 RBAC 与关系型权限，并在 PostgreSQL RLS 层真正执行。

## 5. 数据互通

所有客户端访问同一机构云数据库。不存在“手动同步”按钮：保存即进入云端，其他有权限的用户读取最新数据。

V1 不追求 Google Docs 式同字段多人实时协同编辑，优先保证：

- 保存后全员看到最新版
- 冲突可检测
- 关键修改有审计记录

## 6. 安全边界

- 禁止将真实学生隐私数据提交 GitHub。
- 禁止将 Supabase service key、数据库密码等密钥提交仓库。
- 开发阶段使用虚构数据。
- 关键业务操作写 audit_log。
- 正式上线前单独完成未成年人信息保护、备份、权限审计与部署合规评估。

## 7. AI 边界

AI 仅用于辅助结构化、摘要、重复问题识别、家校反馈草拟、教研案例推荐等。

AI 生成内容必须可追溯，正式学情状态变更必须由教师确认。
