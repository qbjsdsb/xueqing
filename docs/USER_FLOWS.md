# 核心用户流程

> 本文把产品蓝图翻译成可直接用于设计、开发和验收的用户流程。开发新页面前优先检查它是否服务这些流程。

## Flow A｜机构首次初始化

**角色：受信任运维 + 首位管理员**

1. 在 Production 建立 organization；
2. 通过一次性受控 bootstrap 创建首位 active org_admin membership；
3. 首位管理员完成登录；
4. bootstrap 入口关闭；
5. 管理员进入成员管理。

### 验收
- 客户端没有超级管理员 Secret；
- 普通注册用户无法自行成为 org_admin；
- bootstrap 完成后不能被重复滥用。

---

## Flow B｜管理员邀请教师

### B1. 新邮箱
1. 管理员进入成员管理；
2. 输入教师邮箱与预期角色；
3. 服务端验证管理员、机构与角色；
4. 创建 `organization_invitation(pending)`；
5. Auth Admin 发送邀请；
6. 记录 Auth User ID / sent_at；
7. 教师通过邮件完成 Auth 激活；
8. App 通过受控流程验证当前 Auth User 与 pending invitation；
9. 创建 active membership + roles；
10. invitation → accepted；
11. 管理员再按需要分配学生/学科。

### B2. 已有 pending invitation
1. 管理员看到“已邀请，尚未加入”；
2. 可以重发或取消；
3. 重发复用同一 invitation；
4. 不创建重复 membership。

### B3. 已经是目标机构 active member
系统不再发送“加入机构”邀请，而是进入已有成员详情、角色调整或密码恢复等正确流程。

### B4. 邮箱是已确认平台账号，但不是目标机构成员
如果 V1 尚未实现跨机构 `link-existing-user`：
- 明确提示当前版本暂不支持该场景；
- 不重复创建 Auth User；
- 不用失败 invite 流程硬绕。

### 验收
- pending invitation 没有学生数据权限；
- 邀请过期/失败可安全重试；
- 重发不产生重复 invitation/member；
- Windows/Android 回跳都能完成；
- 已确认邮箱不会错误走“新用户 invite”；
- Auth 成功而 membership 激活未完成时可以安全恢复。

---

## Flow C｜建立学生主档案

1. 管理员/授权人员点击新建学生；
2. 输入最少必要身份信息；
3. 系统执行可能重复提示；
4. 若已有学生，进入已有主档案；
5. 若确认为新学生，创建 student；
6. 创建当前 enrollment；
7. 启用所需 subject profile；
8. 分配任课教师/学生负责人。

### 验收
- 姓名不做硬唯一键；
- 不因不同学科重复建 student；
- 年级和负责人变化保留历史；
- 普通教师不能用“删掉重建”绕过查重治理。

---

## Flow D｜老师第一次接手学生

1. 教师打开学生；
2. 首屏看到当前重点案例、待验证、下一步行动、最近时间线；
3. 可按学科进入详细案例；
4. 必要时查看允许共享的综合摘要；
5. 不需要翻完整历史才能知道下一步。

### 验收
- 新教师短时间内能回答“现在最重要的 3 件事是什么”；
- 历史负责人和过去处理记录仍可追溯；
- 无权学科详细内容不会意外暴露。

---

## Flow E｜课堂中快速发现一个新问题

目标不是当场填完整档案，而是**不中断教学地捕捉事实**。

1. 教师在课程/学生页点击“发现问题”；
2. 当前学生和学科已知时不重复询问；
3. 输入一句最小标题，例如“人物形象题只写性格，没有文本依据”；
4. 可选补一句说明；
5. 可选立即选择分类或附证据；
6. 系统提示明显重复案例；
7. 保存为 `new` 草稿；
8. 网络异常时先保留本地草稿。

### 目标体验
- 常见捕捉目标 10–20 秒；
- 不强迫课中选择完整 taxonomy；
- 不强迫上传图片；
- 不强迫当场写根因和整改方案；
- 不强迫当场建下一步行动。

### 验收
课堂节奏不会为了“把系统填完整”被打断。

---

## Flow F｜把 `new` 草稿确认成正式案例

通常发生在课后整理或教师主动进入草稿时。

1. 打开 `new` 草稿；
2. 系统利用当前 lesson context 预填学生、学科、发现时间；
3. 教师确认轻量 taxonomy 和 case type；
4. 系统可把课堂短备注 + lesson context 转成一条最小 classwork/observation evidence 草稿；
5. 教师确认或补充证据，不要求上传附件；
6. 确认 owner；
7. 创建首个主行动，或明确 pause reason；
8. 执行 `confirm_case`；
9. 写 confirmed event。

### 验收
- 正式案例有可解释来源；
- 数据质量在课后补齐，而不是把负担塞进课中；
- 同类历史案例可在确认前提示复用/reopen；
- `new → confirmed` 是受控命令，不靠页面随便改 status。

---

## Flow G｜一次真实课程

### 课前
1. 从“今日”或学生页快速开始课程；
2. 看到到期行动、待验证和重点案例。

### 课中
3. 完成/调整已有行动；
4. 记录真正发生的干预；
5. 有验证时记录 assessment；
6. 新问题走 Flow E 快速捕捉。

### 课后
7. 系统整理本节新增事实；
8. 教师确认必要状态变化；
9. 必要的 `new` 草稿进入 Flow F，或保留为待整理；
10. 完成旧主行动；
11. 确认/创建下一步主行动；
12. 通过事务化 `complete_lesson` 完成课程。

### 验收
- 常规课后记录中位时间 ≤ 60 秒；
- 不要求填写另一份周总结；
- 课程结果不会在两张事实表重复保存；
- 网络失败不清空当前输入；
- 多表写入不会留下“课已完成但行动/验证只写了一半”的状态。

---

## Flow H｜验证失败

1. 教师记录 assessment = failed / partial；
2. 系统不自动关闭案例；
3. 提示继续干预或原因复盘；
4. 教师选择下一步主行动；
5. 案例回到/保持 intervening；
6. 历史 assessment 保留。

### 验收
- failed 不产生“已稳定”；
- 历史验证保留；
- 新行动和旧行动关系清楚。

---

## Flow I｜验证通过并进入稳定观察

1. 教师记录 assessment = passed；
2. 系统显示“本次验证通过”，但不自动等同 stable/closed；
3. 教师结合证据确认是否进入 stable；
4. stable 可以设置后续观察/复查行动；
5. 观察完成后才退出主动跟进并 closed。

### 验收
- assessment result 与 case status 不混淆；
- stable 有改善依据；
- closed 时不存在冲突 pending 主行动；
- 以后复发通过 reopen 原案例。

---

## Flow J｜问题复发

1. 教师发现与历史案例高度相同的问题；
2. 系统提示已有 stable/closed 案例；
3. 教师选择 reopen，而不是新建重复案例；
4. 增加本次新证据；
5. `reopened_count` 增加；
6. 创建新的主行动；
7. 原历史完整保留。

### 验收
- 不制造多个互相重复的“同一问题”；
- 原来为什么稳定/关闭、现在为什么重开都可追溯。

---

## Flow K｜教师离职与交接

1. 管理员选择待停用成员；
2. 系统列出 active teacher/staff assignments；
3. 列出未结束案例 owner；
4. 列出 pending actions；
5. 管理员选择接手人员或明确处理方式；
6. 受控事务结束旧关系、建立新关系、转交当前责任；
7. 验证没有意外 orphan 责任项；
8. membership disabled；
9. 历史事实仍显示原教师。

### 验收
- 不会“教师一删，历史作者全变 null”；
- 不会先停用账号再发现一堆未交接任务；
- 没有未完成行动悄悄失去负责人；
- 旧 Token 也不能继续访问机构数据。

---

## Flow L｜网络失败与重试

1. 教师正在填写课后记录；
2. 网络断开/请求超时；
3. 页面显示保存失败或本地草稿；
4. 输入仍在；
5. 网络恢复后用户重试；
6. 简单 insert 复用原 UUID，多表命令复用 operation id；
7. 服务端如果第一次其实已成功，第二次不重复副作用；
8. 云端确认后显示已保存并清理草稿。

### 验收
- 不出现“UI 显示成功但数据库没有”；
- 不因连点重试生成重复 intervention/assessment/case；
- App 意外退出后关键草稿可恢复。

---

## Flow M｜跨学科查看

1. 任课教师进入自己负责学生；
2. 可看到本科详细学情；
3. V1 只提供必要基础/综合摘要；正式综合观察流在 V1.5 扩展；
4. 不能修改其他学科专业案例；
5. 学生负责人拥有更广综合视角，但不能替任课老师重写专业结论。

### 验收
前端和数据库行为一致；手工请求也无法越权。

---

## Flow N｜合并重复学生

1. 管理员确认两份档案属于同一真实学生；
2. 系统展示 source / target 和受影响数据；
3. 管理员选择保留 target；
4. `merge_students` 验证同机构、权限、无 merge 环；
5. 当前关系与引用按规则迁移/重指向；
6. source → merged，并记录 `merged_into_student_id`；
7. 写 student_merge_record + audit；
8. 旧 source ID 仍能解释“已合并到哪位学生”。

### 验收
- 不静默丢课程/案例历史；
- 不能跨机构合并；
- 普通教师不能执行；
- 重试不会执行两次迁移。

---

## V1 不应出现的流程

以下流程如果开发过程中突然出现，应先回到产品评审：
- 为了进入课程必须先排完整课表；
- 老师每周重新抄一份周报数据；
- 同一问题在“初诊/顽固/周跟进”三处维护；
- 课堂中为了记录一个问题必须填十几个字段；
- pending invitation 已经可以读取学生数据；
- 重发邀请会再建一个机构成员；
- 普通教师可以删除历史事实；
- 页面直接任意 UPDATE learning_cases.status；
- 完成一节课依赖多次互不事务化请求且允许半成功；
- 网络失败后要求老师重新填一遍；
- 一次 passed 自动等于“问题已解决”；
- AI 自动把学生状态改成“已解决”。
