# 核心用户流程

> 本文把产品蓝图翻译成可直接用于设计、开发和验收的用户流程。开发新页面前优先检查它是否服务这些流程。

## Flow A｜机构首次初始化

**角色：受信任运维 + 首位管理员**

1. 在 Production 建立 organization；
2. 通过一次性受控 bootstrap 创建首位 org_admin membership；
3. 首位管理员完成登录；
4. bootstrap 入口关闭；
5. 管理员进入成员管理。

### 验收
- 客户端没有超级管理员 Secret；
- 普通注册用户无法自行成为 org_admin；
- bootstrap 完成后不能被重复滥用。

---

## Flow B｜管理员邀请教师

1. 管理员进入成员管理；
2. 输入教师邮箱与预期角色；
3. 服务端验证管理员权限；
4. 创建/关联 Auth User 与 membership；
5. 教师完成首次激活；
6. 管理员把学生/学科分配给教师。

### 验收
- 教师登录后只能看到有权机构；
- 没有 assignment 的 teacher 不自动看到全部学生；
- 邀请失败有可理解错误，不产生半条脏 membership。

---

## Flow C｜建立学生主档案

1. 管理员/授权人员点击新建学生；
2. 输入最少必要身份信息；
3. 系统执行可能重复提示；
4. 若已有学生，进入已有主档案；
5. 若确认为新学生，创建 student；
6. 创建当前 enrollment；
7. 启用所需 subject profile；
8. 分配任课教师/学生负责人。

### 验收
- 姓名不做硬唯一键；
- 不因不同学科重复建 student；
- 年级和负责人变化保留历史。

---

## Flow D｜老师第一次接手学生

1. 教师打开学生；
2. 首屏看到：当前重点案例、待验证、下一步行动、最近时间线；
3. 可按学科进入详细案例；
4. 必要时查看允许共享的综合摘要；
5. 不需要翻完整历史才能知道下一步。

### 验收
- 新教师在短时间内能回答“现在最重要的 3 件事是什么”；
- 历史负责人和过去处理记录仍可追溯；
- 无权学科的详细内容不会意外暴露。

---

## Flow E｜快速发现一个新学情问题

课堂中“发现问题”必须允许快速捕捉，不能要求老师当场完成完整诊断。

### 快速捕捉
1. 教师在学生/课程中点击“发现问题”；
2. 输入自然语言标题/表现；
3. 可选：立即选择受控分类和添加证据；
4. 系统提示可能重复案例；
5. 教师可以保存为 `new` 草稿案例。

### 确认进入正式跟进
6. 教师补充/确认受控分类；
7. 补充必要证据或证据来源；
8. 完成初步原因判断（如果当前能判断）；
9. 执行 `confirm_case`；
10. 创建首个主行动，或明确 pause_reason。

### 验收
- 课堂中 10–20 秒也能先把问题抓住；
- `new` 可以暂时没有 taxonomy/action，不强迫老师边上课边填完整表；
- 进入 `confirmed` 后再要求结构化口径和下一步；
- 受控分类用于统计，自由文本用于真实表达；
- 重复案例不会无限新建。

---

## Flow F｜一次真实课程

### 课前
1. 从“今日”或学生页快速开始课程；
2. 看到该学生到期行动、待验证和重点案例。

### 课中
3. 记录真正发生的干预；
4. 有验证时记录 assessment；
5. 新发现问题时快速建立 `new` 草稿案例。

### 课后
6. 系统整理本节发生的事实；
7. 教师确认必要状态变化；
8. 完成旧主行动；
9. 确认/创建下一步主行动；
10. 完成课程。

### 验收
- 常规课后记录中位时间 ≤ 60 秒；
- 不要求填写另一份“周总结”；
- 课程结果不会在两张事实表重复保存；
- 网络失败不清空当前输入；
- 完成课程是事务化命令，不留下半套状态。

---

## Flow G｜验证失败

1. 教师记录 assessment = failed / partial；
2. 系统不自动关闭案例；
3. 提示继续干预或原因复盘；
4. 教师选择下一步主行动；
5. 案例回到/保持 intervening。

### 验收
- failed 不产生“已稳定”；
- 历史验证保留；
- 新行动和旧行动关系清楚。

---

## Flow H｜验证通过并进入稳定观察

1. 教师记录 assessment = passed；
2. 系统显示“验证通过”，但不自动等同 stable/closed；
3. 教师结合证据确认是否进入 stable；
4. stable 阶段可以设置后续观察/复查行动；
5. 观察完成后才关闭主动跟进。

### 验收
- assessment result 与 case status 不混淆；
- closed 时不存在冲突 pending 主行动；
- 以后复发通过 reopen 命令重新激活原案例。

---

## Flow I｜问题复发

1. 教师发现与历史案例高度相同的问题；
2. 系统提示已有 stable/closed 案例；
3. 教师选择 reopen；
4. reopen 作为业务命令/事件，将案例重新进入合适的 active 状态，而不是创建一个名为 `reopened` 的新状态；
5. 增加新证据；
6. `reopened_count` 增加；
7. 创建新的主行动。

### 验收
- 不制造多个相互重复的“同一问题”；
- 原来为什么关闭、现在为什么重开都可追溯。

---

## Flow J｜教师离职与交接

1. 管理员选择待停用成员；
2. 系统列出 active teacher/staff assignments、未结束案例 owner、pending actions；
3. 管理员选择接手人员；
4. 受控事务结束旧关系、建立新关系、转交当前责任；
5. membership disabled；
6. 历史事实仍显示原教师。

### 验收
- 没有“教师删掉以后历史作者全变成 null”；
- 没有未完成行动悄悄失去负责人；
- 停用账号不能继续读取机构数据。

---

## Flow K｜网络失败

1. 教师正在填写课后记录；
2. 网络断开；
3. 页面显示保存失败/本地草稿；
4. 输入内容仍在；
5. 网络恢复后用户重试；
6. client-generated UUID / operation id 防止重复创建；
7. 云端确认后显示已保存并清理草稿。

### 验收
- 不出现“UI 显示成功但数据库没有”；
- 不因为连点重试生成重复 intervention/case；
- App 意外退出后关键草稿可恢复。

---

## Flow L｜跨学科查看

1. 任课教师进入自己负责学生；
2. 可看到本科详细学情；
3. V1 只提供必要的基础/综合摘要；正式综合观察流在 V1.5 扩展；
4. 不能修改其他学科专业案例；
5. 学生负责人拥有更广综合视角，但不能替任课老师重写专业结论。

### 验收
前端和数据库行为一致；手工请求也无法越权。

---

## V1 不应出现的流程

以下流程如果开发过程中突然出现，应先回到产品评审：
- 为了进入课程必须先排完整课表；
- 老师每周重新抄一份周报数据；
- 同一问题在“初诊/顽固/周跟进”三处维护；
- 老师为了快速捕捉一个新问题必须先填写十几个字段；
- 普通教师可以删除历史事实；
- 页面直接任意 UPDATE learning_cases.status；
- 完成一节课依赖多次互不事务化的请求且允许半成功；
- 网络失败后要求老师“重新填一遍”；
- AI 自动把学生状态改成“已解决”。
